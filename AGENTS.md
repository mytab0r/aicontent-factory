# AGENTS.md — aicontent-factory

Автономный конвейер генерации ИИ-контента (музыка/видео/faceless-каналы) для
публикации на YouTube/Spotify/др. с целью долгосрочного пассивного дохода.
Полностью автоматизированный цикл: идея -> генерация -> сборка -> публикация -> аналитика.

## Золотые правила
1. YAGNI. Не строить инфраструктуру "на вырост" — только то, что нужно для
   текущего работающего пайплайна. Один рабочий сценарий (напр. lo-fi
   YouTube-канал) лучше пяти недоделанных.
2. Никаких новых внешних SaaS-подписок/платных API без явного решения —
   сначала использовать 9router (`http://9router:20128` внутри docker-сети,
   публично `https://9router.pxbt.app`) для LLM/TTS/image. Ключ: `ROUTER_API_KEY`
   из `/opt/stack/hermes/.env` (или свой `.env` в этом проекте).
3. Все секреты (YouTube API, Spotify/DistroKid, Suno/Udio если понадобятся) —
   через vault/.env на сервере, никогда в код/git.
4. Площадки требуют пометку синтетического контента (YouTube "Altered or
   synthetic content") — закладывать это в процесс публикации с самого начала,
   не постфактум.
5. Порядок разработки: сначала тест (фиксирует требуемое поведение, пишется
   ДО реализации), потом минимальный код под него, потом push в CI. Все
   гейты (lint/test/build) — через GitHub Actions, не гонять тяжёлое (сборки,
   Playwright, большие npm install и т.п.) локально на 1 vCPU сервере;
   локальный прогон — только быстрая проверка разработчика, не финальный гейт.
   Задача на kanban-доске не Done, пока CI-прогон её коммита не подтверждён
   `success` (`gh run list`/`gh run watch`) — никогда не закрывать задачу
   по одному локальному прогону и никогда не оставлять её Done при красном/
   висящем CI.
6. Каждый прогон пайплайна должен быть воспроизводим и логируем (что
   сгенерено, что опубликовано, метрики) — без этого нельзя итерировать.

  решения приёма оплат и доступа.
- Новые платные SaaS/API-подписки мимо 9router — золотое правило 2: никаких
  расходов до первого дохода без явного решения владельца.
- Инфраструктура «на вырост» под несколько ниш — правило 1 YAGNI: один
  работающий lo-fi пайплайн лучше пяти недоделанных.
- sleep-ожидание внутри HF ZeroGPU раннера — квота горит и на FAILED-ретраи;
  только fail-fast скрипт + внешний cron с resume-стейтом.

## Флоу задачи — единый для всех проектов (autopilot, aicontent-factory, tonproxy, gc-estimates, business-hive)
Текст между маркерами flow-block одинаков во всех AGENTS.md; расхождение — баг.
Проверка: `python3 /opt/data/scripts/agents_flow_block.py check <пути к AGENTS.md>`.

0. Критерии приёмки — при создании задачи, проверяемые: «команда Y возвращает Z»,
   «URL отвечает 200», «тест T зелёный», а не «сделать X».
1. TDD. Сначала тест, фиксирующий требуемое поведение, и он падает (RED); затем
   минимальный код, пока тест не позеленеет (GREEN); затем рефакторинг при
   зелёных тестах. Без теста — только правки доков/конфигов без логики.
2. CI-гейт. Коммит пушится в ветку; задача не готова, пока CI-прогон именно этого
   коммита не `success` (`gh run list` / `gh run watch`). Локальный прогон — не
   гейт. Красный или висящий CI = не готово. Где CI нет — гейт = команда из
   критериев приёмки, её вывод прикладывается как доказательство.
3. request-review. Воркер не закрывает нетривиальную задачу сам: вместо `complete` —
   `hermes kanban request-review --summary "что сделано + как проверено + какие
   критерии закрыты (доказательства: команда+вывод, ссылка на CI-прогон, URL)"`.
   Ревьюер (другой профиль) делает `complete` только после проверки
   доказательств, не по доверию к тексту; иначе `request-changes`.
   Прямой `complete` — только для тривиального без риска регресса (опечатка в доке).
4. Что НЕ строим. У задачи есть раздел «Не-цели»: что сознательно не делаем,
   у каждого пункта — причина. Не строить то, что не выводится из критериев
   приёмки; идея «заодно» — отдельная карточка, не расширение текущей.
5. Как спрашивать. Если заблокирован — один вопрос за раз, со своим
   рекомендованным вариантом и причиной выбора; не спрашивать то, что
   выводится из кода, доков или git-истории.
